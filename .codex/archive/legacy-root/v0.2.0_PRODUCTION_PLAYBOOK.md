## 1. Operational Runbooks

### Runbook 1: Traffic Ramp Procedure

**Purpose**: Gradually shift production traffic from v0.1.0 to v0.2.0 using a 3-stage controlled rollout

**Trigger**: Post-deployment validation complete (Phase 4 PASS)

**Prerequisites**:
- ✅ v0.2.0 fully deployed to production
- ✅ All 4 lanes certified (Cognitive, RAG, ML, Quantum)
- ✅ Performance monitoring active
- ✅ Incident response team on standby

#### Stage 1: 10% Traffic Ramp (30 min minimum)

1. **Initiate ramp** (T+0)
   - Execute: `./ops/ramp_traffic.sh --stage 1 --percent 10`
   - Verify: Check unified-governance-gate metrics reporting
   - Expected: Error rate baseline established within 2 min

2. **Monitor metrics** (T+0 to T+30 min)
   - Collect: Latency, error rate, resource utilization
   - Gates to monitor:
     - Error rate: must be <0.1% (baseline is 0.03%)
     - Latency p99: must be <500ms (baseline is 150ms)
     - CPU utilization: must be <40% (v0.2.0 optimized)
   - Alert threshold: Any metric exceeds gate value
   - Action if gate fails: STOP ramp, execute Stage 1 Rollback (below)

3. **Sign-off** (T+30 min)
   - Review unified-governance-gate report
   - Confirm all metrics within bounds
   - Incident Commander signs off or escalates

#### Stage 2: 25% Traffic Ramp (45 min minimum)

1. **Increase ramp** (T+30 min)
   - Execute: `./ops/ramp_traffic.sh --stage 2 --percent 25`
   - Verify: Check ramping is smooth (no discontinuities)
   - Expected: Latency may increase 5-10%, error rate unchanged

2. **Monitor metrics** (T+30 to T+75 min)
   - Same gates as Stage 1
   - Additional gates for Stage 2:
     - Database connection pool: <85% utilization
     - Memory pressure: <60%
   - Alert threshold: Same as Stage 1
   - Action if gate fails: Execute Stage 2 Rollback (below)

3. **Sign-off** (T+75 min)
   - Review metrics, confirm all gates PASS
   - If gates PASS: Proceed to Stage 3
   - If gates FAIL: Escalate to Tier 2 incident commander

#### Stage 3: 100% Traffic Ramp (LIVE)

1. **Complete ramp** (T+75 min)
   - Execute: `./ops/ramp_traffic.sh --stage 3 --percent 100`
   - Verify: All traffic now routing to v0.2.0
   - Expected: Error rate stable, latency normalized

2. **Stabilization period** (T+75 to T+120 min)
   - Monitor enhanced alerting (every 5 min)
   - Check all subsystems: Cognitive, RAG, ML, Quantum
   - Verify no cascading failures
   - Database transaction rate: steady
   - Queue depths: normal range

3. **Go-Live Certification** (T+120 min)
   - If all gates PASS: v0.2.0 officially LIVE
   - If any gates FAIL: Trigger rollback procedures (see below)

**Rollback Procedures**:

**Stage 1 Rollback** (if metrics fail during 10% ramp):
```bash
# Immediate action
./ops/ramp_traffic.sh --rollback --target 0
./ops/verify_rollback.sh --version v0.1.0

# Investigation
./analysis/collect_logs.sh --start "T-15min" --end "NOW" > /tmp/stage1_failure.log
# Send logs to incident channel
```

**Stage 2 Rollback** (if metrics fail during 25% ramp):
```bash
# Immediate action
./ops/ramp_traffic.sh --rollback --target 10
./ops/verify_rollback.sh --version v0.1.0

# Cool down (15 min at 10% before full rollback decision)
./monitoring/check_stability.sh --duration 15min

# If stable: Return to v0.1.0 or investigate further
# If unstable: Execute full rollback
./ops/ramp_traffic.sh --rollback --target 0
```

**Stage 3 Rollback** (if LIVE issues detected):
```bash
# Emergency action
./ops/ramp_traffic.sh --rollback --target 0
./ops/verify_rollback.sh --version v0.1.0

# Critical incident response (see Section 5 Emergency Procedures)
```

### Runbook 2: Incident Response (<2min SLA)

**Purpose**: Respond to Sev-1 production incidents within 2 minutes

**Trigger**: CRITICAL alert OR manual escalation

**SLA Target**: <120 seconds from detection to mitigation start

#### Sev-1 Incident Response Procedure

**T+0s - Detection & Classification**
- Incident automatically detected by monitoring
- ci-emergency-response-agent activates
- Classify incident:
  - Traffic/routing issue → RUN: traffic_ramp_rollback.sh
  - Data/database issue → RUN: database_failover.sh
  - Service crash → RUN: service_restart.sh
  - External dependency → RUN: circuit_breaker.sh

**T+10s - Incident Commander Notification**
- Slack alert to @incident-commander-tier1
- Page rotation check (who is on-call?)
- Incident log created automatically
- Status page updating begins (every 30 sec)

**T+20s - Runbook Execution Start**
- ci-emergency-response-agent executes relevant runbook
- Monitoring dashboard linked in incident Slack thread
- Team members notified based on incident type

**T+30s - Tier 2 Escalation (if not resolved)**
- If Tier 1 incident commander not responding
- Automatically escalate to @incident-commander-tier2
- Tier 2 takes command of incident
- May override Tier 1 decisions if critical

**T+60s - Tier 3 Escalation (if not resolved)**
- If Tier 2 not responding
- Automatically escalate to @incident-commander-tier3 (engineering director)
- System enters emergency mode (more aggressive interventions allowed)
- Decision authority elevated

**T+90s - Status Report Required**
- Incident must be in one of these states:
  - RESOLVED (automatic resolution succeeded)
  - IN_PROGRESS (manual work underway, ETA <30 min)
  - ESCALATED (waiting for Tier 3 decision)
  - ROLLBACK (full rollback to v0.1.0 in progress)

**T+120s - SLA Review**
- If still not resolved: Incident violates SLA
- Requires manual escalation decision
- Log SLA violation for retrospective

#### Incident Response Runbooks

**Runbook: traffic_ramp_rollback.sh**
- Usage: `./ops/runbooks/traffic_ramp_rollback.sh`
- Purpose: Immediately ramp traffic back to v0.1.0
- Duration: <30 seconds to complete
- Verification: Confirm 100% traffic on v0.1.0
- Notification: Send incident summary to @incident-channel

**Runbook: database_failover.sh**
- Usage: `./ops/runbooks/database_failover.sh`
- Purpose: Fail over database to standby (if applicable)
- Duration: <60 seconds to complete
- Verification: Confirm read/write operations resuming
- Notification: Send failover status to @ops-team

**Runbook: service_restart.sh**
- Usage: `./ops/runbooks/service_restart.sh --service <service_name>`
- Purpose: Restart individual service in graceful manner
- Duration: <45 seconds per service
- Verification: Service health checks passing
- Notification: Update incident log

**Runbook: circuit_breaker.sh**
- Usage: `./ops/runbooks/circuit_breaker.sh --dependency <name> --state open`
- Purpose: Open circuit breaker for failing external dependency
- Duration: <10 seconds
- Fallback: Service operates in degraded mode
- Notification: Customer-facing status page updated

**Runbook: status_page_update.sh**
- Usage: `./ops/runbooks/status_page_update.sh --status INVESTIGATING --message "..."`
- Purpose: Update public status page with incident details
- Duration: <5 seconds
- Frequency: Every 30 seconds during incident
- Notification: Automatically informs customers

### Runbook 3: Rollback Procedure

**Purpose**: Emergency revert from v0.2.0 to v0.1.0 if critical issues detected

**Trigger**: 
- Incident Response SLA violated AND cannot resolve
- Multiple SLA breaches in rapid succession
- Manual decision by Incident Commander Tier 1 or higher

**Maximum Duration**: 5 minutes from decision to rollback complete

#### Full Rollback Steps

1. **Decision & Authorization** (T+0s)
   - Incident Commander decides rollback necessary
   - Executes: `./ops/rollback.sh --version v0.1.0 --force`
   - Confirm: "ARE YOU SURE? This will revert to v0.1.0" → Y

2. **Traffic Ramp to v0.1.0** (T+5 to T+35s)
   - Ramp: 100% → 75% → 50% → 25% → 0% (on v0.2.0)
   - In parallel: 0% → 25% → 50% → 75% → 100% (on v0.1.0)
   - Duration: 30 seconds controlled ramp
   - Monitoring: Error rate, latency should improve during ramp

3. **Verification** (T+35 to T+60s)
   - Confirm: 100% traffic on v0.1.0
   - Check: Error rate baseline restored
   - Check: Latency normalized
   - Database: All write operations back to v0.1.0
   - Cache: Invalidate v0.2.0-specific cache entries

4. **Post-Rollback Stabilization** (T+60 to T+120s)
   - Monitor for any issues with v0.1.0
   - Confirm no data corruption occurred during transition
   - Alert resolution: Clear all v0.2.0-related incidents from active queue
   - Status page: Update to "RECOVERED - Investigating Root Cause"

5. **Incident Documentation** (T+120s+)
   - Incident incident log finalized
   - Root cause analysis scheduled (within 24 hours)
   - Communications to stakeholders
   - All teams notified of rollback

#### Rollback Decision Matrix

| Scenario | SLA Breached | Decision | Action |
|----------|--------------|----------|--------|
| Single metric spike (err <2s) | No | MONITOR | Continue monitoring, no action |
| Error rate >1% sustained 30s | Yes | INVESTIGATE | Tier 1 investigates, decide within 60s |
| Error rate >5% sustained 60s | Yes | ROLLBACK | Automatic rollback initiated |
| Data corruption detected | Yes | ROLLBACK | Immediate rollback + incident mode |
| Cascading failures in 2+ lanes | Yes | ROLLBACK | Immediate rollback + incident mode |

### Runbook 4: Scaling Procedure

**Purpose**: Scale production deployment horizontally or vertically if resource utilization approaches limits

**Trigger**:
- CPU utilization: sustained >70% for 5+ minutes
- Memory: >80% for 5+ minutes
- Database connections: >85% of pool for 5+ minutes
- Request queue depth: growing steadily

#### Horizontal Scaling (Add More Instances)

1. **Assessment** (Automated)
   - Check: Current instance count (baseline: 10 instances)
   - Check: Metrics trend (is load increasing or spike?)
   - Decision: Add 2-4 instances (30-40% increase)

2. **Provision New Instances** (T+0 to T+120s)
   - Launch: 3 new v0.2.0 instances in load balancer pool
   - Configuration: Identical to existing instances
   - Pre-warming: Route 1% test traffic to verify health

3. **Gradual Load Shift** (T+120s to T+300s)
   - Shift load: 1% → 5% → 10% → 25% → 50% → 100%
   - Monitoring: Per-instance latency & error rate stable
   - Duration: 3 minutes gradual (allows connection re-balancing)

4. **Verification & Stability** (T+300s+)
   - Overall metrics: Back to <60% utilization
   - Per-instance metrics: Evenly distributed
   - Alert resolution: Scale-related alerts clear
   - Documentation: Log scaling event

#### Vertical Scaling (Increase Instance Size)

1. **Rolling Update Process**
   - Current instances: 10x (size: medium)
   - New size: large (50% more CPU/memory)
   - Update strategy: 1 instance at a time

2. **Update Single Instance** (repeat for each instance)
   - Remove instance from load balancer
   - Stop service gracefully (allow in-flight requests to complete)
   - Upgrade instance size
   - Start service with new resources
   - Add back to load balancer
   - Wait 2 minutes for stabilization
   - Repeat for next instance

3. **Total Duration**: ~20 minutes (10 instances × 2 min each)

#### Scaling Decision Matrix

| Metric | Threshold | Action | Time to Execute |
|--------|-----------|--------|-----------------|
| CPU | >70% sustained 5min | +3 instances (horizontal) | 5 minutes |
| Memory | >80% sustained 5min | +3 instances (horizontal) | 5 minutes |
| Connections | >85% 5min | +3 instances (horizontal) | 5 minutes |
| Queue depth | Growing >10/sec | Vertical scale instances | 20 minutes |
| Latency p99 | >1s sustained 2min | Investigate bottleneck | Variable |

### Alert Thresholds & Response

**Yellow Alerts** (Investigation phase)
- Triggered when metric reaches yellow threshold
- Send notification to #dev-notifications
- Do NOT page incident commander (unless sustained >5 min)
- Engineer investigates within 15 minutes

**Red Alerts** (Incident phase)
- Triggered when metric reaches red threshold
- Page Tier 1 Incident Commander immediately
- Create incident in tracking system
- Execute relevant runbook within 2 minutes

**Alert Fatigue Prevention**:
- Minimum 5-minute duration before alert fires
- Transient spikes <30 sec ignored
- Grouped alerts (multiple failures) → single page

## 4. Change Management

### Deployment Approval Process

**Step 1: Change Request Submission**
- Who: Deployment engineer
- What: Submit change request to change advisory board (CAB)
- When: 48 hours before planned deployment
- Template: Use `.codex/CHANGE_REQUEST_TEMPLATE.md`

**Step 2: Risk Assessment**
- CAB evaluates: Impact, scope, rollback feasibility
- Result: Low/Medium/High risk classification
- Approval: Low risk → 1 reviewer, Medium → 2 reviewers, High → Full CAB

**Step 3: Pre-Deployment Checks**
- Code review: 100% coverage required
- Security scan: 0 CRITICAL/HIGH vulns required
- Test coverage: 1000+ tests passing required
- Performance baseline: Established before deployment

**Step 4: Traffic Ramp Requirement**
- ALL deployments require 3-stage traffic ramp
- Stage 1: 10% traffic, 30 min minimum
- Stage 2: 25% traffic, 45 min minimum
- Stage 3: 100% traffic, LIVE
- No exception (unless explicitly approved by @mbaetiong)

**Step 5: Post-Deployment Validation**
- Monitoring period: 120 minutes minimum
- SLA verification: Error rate, latency, uptime
- Decision: Mark as SUCCESSFUL or ROLLBACK

### Rollback Decision Criteria

**Automatic Rollback Triggered If**:
- Error rate >0.5% sustained >2 min
- Latency p99 >1000ms sustained >2 min
- Database corruption detected
- Multiple critical incidents in <30 min
- Customer impact >5% of user base

**Manual Rollback Decision If**:
- Performance degradation >20% vs baseline
- Unexpected resource consumption spike
- Third-party dependency issues
- Business decision (e.g., feature not ready)

## 5. Emergency Procedures

### Sev-1 Incident Response (<2min SLA)

**IF**: Any of these occur
- Error rate >0.5% sustained >30 sec
- All systems down or inaccessible
- Data loss/corruption detected
- Security breach suspected

**THEN**: Execute immediately
1. Page @incident-commander-tier1 NOW
2. Create incident: `./ops/create_incident.sh --severity sev1`
3. Execute runbook: `./ops/runbooks/[relevant_runbook].sh`
4. Update status page: Every 30 seconds
5. Tier 1 makes decision: CONTINUE or ROLLBACK

**T+2min**: Decision required
- If resolved: Document in incident log
- If unresolved: Escalate to Tier 2

### Sev-2 Incident Response (<5min SLA)

**IF**: Any of these occur
- Error rate 0.1-0.5%
- Latency p99 500-1000ms
- 1-5% user impact
- Non-critical service degradation

**THEN**: Execute within 5 minutes
1. Notify @incident-commander-tier1 (not paged)
2. Create incident: `./ops/create_incident.sh --severity sev2`
3. Investigate root cause
4. Execute fix or escalate to Tier 2

**T+5min**: Status update required
- Estimated time to resolution
- Decision: Continue or escalate

### Sev-3 Incident Response (<15min SLA)

**IF**: Any of these occur
- Minor performance issues
- Isolated failures (<0.1% impact)
- Monitoring false positives

**THEN**: Execute within 15 minutes
1. Create ticket: `./ops/create_ticket.sh --type incident --severity sev3`
2. Investigate when possible
3. Document in ticket for weekly review

### Cascading Failure Recovery

**IF Multiple Failures Detected** (2+ issues simultaneously):

1. **Immediate Action**: Automatic rollback to v0.1.0
   - Command: `./ops/rollback.sh --version v0.1.0 --force`
   - Page: Tier 1 + Tier 2 + Tier 3 (all tiers)

2. **Investigation Phase** (post-rollback)
   - Collect logs, traces, metrics
   - Identify what triggered cascading failures
   - Root cause analysis

3. **Prevention** (within 24 hours)
   - Circuit breaker implementation for failing dependency
   - Rate limiting on dependent services
   - Graceful degradation procedures
