## Overview

This document defines the authoritative Python dependency lock file strategy for the _codex_ project. We maintain a **single primary lock** (`uv.lock`) with **derived locks** for specific install surfaces.

## Lock File Hierarchy

```
┌─ pyproject.toml (project manifest, 43 base deps + 30 extras groups)
│
├─ uv.lock (PRIMARY: uv workspace lock, autogenerated)
│  │
│  ├─ requirements/lock.txt (DERIVED: pip-compile from base.txt, transitive closure)
│  │
│  ├─ requirements/lock-eval.txt (DERIVED: eval surface lock, autogenerated)
│  │
│  └─ requirements/lock-ml.txt (DERIVED: ML CPU surface lock, autogenerated)
│
└─ uv.lock acts as the authoritative transitive dependency source
```

## Primary Lock: `uv.lock`

**Authority:** This is the single source of truth for Python dependency resolution.

**Scope:** Complete transitive closure of `pyproject.toml[project].dependencies` and all optional-dependency extras.

**Generation:**
```bash
cd /path/to/_codex_
uv lock --refresh
```

**When to regenerate:**
- After any change to `pyproject.toml` [project] or [project.optional-dependencies]
- Monthly security audit cycle
- When new dependency is added or floor version bumped
- When GitHub Dependabot suggests an update

**Size:** ~353 packages (transitive closure)

**CI integration:** GitHub Actions should:
1. Verify `uv.lock` remains in sync with `pyproject.toml`
2. Commit updates automatically if drift detected
3. Block PR merge if `uv.lock` is stale

## Derived Lock: `requirements/lock.txt`

**Purpose:** Provide a pip-friendly lock file for environments that use `pip install -r` workflows (vs `uv pip install`).

**Scope:** Transitive closure of `requirements/base.txt` (plus manually specified extras).

**Generation:**
```bash
uv pip compile requirements/base.txt \
  --output-file requirements/lock.txt \
  --prerelease=allow \
  --rebuild
```

**When to regenerate:**
- After any change to `requirements/base.txt`
- After regenerating `uv.lock` (to keep in sync)
- Part of the standard Phase 8.4.2 commit workflow

**Size:** ~255 packages

**Use case:** Docker builds, pip-based installs that don't use uv

**CI validation:** Verify transitive closure consistency:
```bash
pip-compile --dry-run requirements/base.txt \
  --output-file /dev/null
```

## Unpinned Surfaces (Optional Locks)

The following requirement files **do not have locks** and are optional; they can be compiled on-demand:

- `requirements-dev.txt` — Development tools (linters, formatters, CI tools)
- `requirements-minimal.txt` — Baseline install
- `requirements-optional.txt` — Feature extras
- `requirements-notebook.txt` — Jupyter environment
- `requirements-audio-transcription.txt` — Audio processing stack
- `requirements-ml-lite.txt` — Alternative CPU ML stack

**Rationale:** These are secondary install surfaces; full reproducibility is optional. Developers using these can either:
1. Run `uv pip compile <file>` locally to generate a lock
2. Rely on `uv lock` for indirect dependency resolution
3. Accept the flexibility of uncompiled transitive resolution

**If future work requires full locks for these surfaces:**
```bash
# Generate all missing locks (Phase 8.4.3+)
for req_file in requirements-dev.txt requirements-minimal.txt \
                requirements-optional.txt requirements-notebook.txt \
                requirements-audio-transcription.txt requirements-ml-lite.txt; do
  uv pip compile $req_file \
    --output-file requirements/lock-${req_file%-*}.txt \
    --rebuild
done
```

## CI/CD Integration (Phase 8.4.3)

### Lock File Validation Workflow

```yaml
# .github/workflows/dependency-lock-check.yml
name: Dependency Lock Consistency

on: [pull_request, push]

jobs:
  lock-sync:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Install uv
        run: pip install uv
      
      - name: Verify uv.lock in sync
        run: uv lock --check
      
      - name: Verify requirements/lock.txt in sync
        run: |
          uv pip compile requirements/base.txt \
            --output-file /tmp/lock-expected.txt \
            --quiet
          diff requirements/lock.txt /tmp/lock-expected.txt || exit 1
      
      - name: Run pip check
        run: |
          pip install --quiet -r requirements/lock.txt
          pip check
      
      - name: Run pip-audit
        run: pip-audit
```

### Auto-Update Workflow (Optional)

When lock files drift from manifest, automatically update them:

```yaml
# .github/workflows/dependency-lock-update.yml
name: Update Locks

on:
  schedule:
    - cron: '0 0 1 * *'  # Monthly
  workflow_dispatch:

jobs:
  update-locks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Install uv
        run: pip install uv
      
      - name: Refresh all locks
        run: |
          uv lock --refresh
          uv pip compile requirements/base.txt \
            --output-file requirements/lock.txt
          uv pip compile requirements-eval.txt \
            --output-file requirements/lock-eval.txt
          uv pip compile requirements-ml-cpu.txt \
            --output-file requirements/lock-ml.txt \
            --extra-index-url https://download.pytorch.org/whl/cpu
      
      - name: Create PR if changed
        uses: peter-evans/create-pull-request@v5
        with:
          commit-message: "chore(deps): refresh lock files"
          title: "chore: refresh dependency lock files"
          branch: deps/refresh-locks
```

## Version Conflict Resolution Process

When GitHub Dependabot or manual audit finds a vulnerable dependency:

1. **Identify the package** and affected surfaces (pyproject, top-level requirements, lock files)
2. **Find the minimum patched version** using `pip index versions <package>`
3. **Update pyproject.toml** if the package appears there (source of truth)
4. **Regenerate uv.lock:**
   ```bash
   uv lock --refresh
   ```
5. **Regenerate derived locks:**
   ```bash
   uv pip compile requirements/base.txt --output-file requirements/lock.txt --rebuild
   # ... and other surface-specific locks
   ```
6. **Verify with pip check:**
   ```bash
   pip install --quiet -r requirements/lock.txt
   pip check
   ```
7. **Commit:** Document the CVE reference in the commit message

## Troubleshooting

### Lock file shows unexpected version

**Check:**
1. Is the constraint too loose in `pyproject.toml`?
2. Did transitive dependencies pull a higher version?
3. Are there incompatible ranges in optional-dependencies?

**Resolution:**
```bash
# Inspect why a package version was chosen
uv pip compile --dry-run requirements/base.txt | grep <package>

# Check dependency tree
pip depgraph
```

### `pip check` fails after lock regeneration

**Likely cause:** Transitive dependencies have conflicting constraints.

**Resolution:**
1. Check if a new dependency was added to `pyproject.toml`
2. Inspect the error message for conflicting specifiers
3. Update the conflicting constraint in `pyproject.toml`
4. Regenerate `uv.lock`

### uv.lock conflicts with pip-compile output

**Why it happens:** Different resolution strategies or index priorities.

**Resolution:**
```bash
# Force pip-compile to match uv resolution
uv pip compile --prerelease=allow --rebuild

# Or vice versa — update pyproject.toml constraints to match pip's resolution
```

## Glossary

| Term | Definition |
|------|-----------|
| **uv.lock** | Workspace lock managed by `uv lock`; authoritative source |
| **requirements/lock.txt** | Pip-friendly lock for `requirements/base.txt` + extras |
| **Transitive closure** | Complete set of direct + indirect dependencies |
| **Lock refresh** | Regenerate lock files to capture new versions/patches |
| **Lock drift** | Lock file out of sync with manifest (pyproject.toml) |
| **Floor version** | Minimum allowed version (e.g., `>=2.13.0`) |
| **Exact pin** | Specific version (e.g., `==5.0.0`) |
| **Range specifier** | Version range (e.g., `>=2.4,<3`) |
