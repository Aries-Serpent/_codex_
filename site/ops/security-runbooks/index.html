    Overview¶

    Purpose¶

    Operational procedures for common security tasks, incident response, and routine maintenance.

    Audience¶

    • On-call security engineers
    • Operations team
    • Incident commanders
    • Compliance officers

    Authentication Runbooks¶

    Runbook 1: Reset User Password¶

    Scenario: User forgot password or account lockout

    Prerequisites: - System admin role - User identity verified (out-of-band)

    Steps:

    1. Verify User Identity 

      # Confirm user details (email, GitHub username, etc.)
curl -H "Authorization: ******" \
  https://api.codex.local/api/v1/users?email=alice@company.com

    2. Initiate Password Reset 

      POST /api/v1/auth/password-reset
{
  "user_id": "alice@company.com",
  "action": "admin_reset"
}

    3. Send Reset Email

    4. System automatically sends reset link
    5. Link expires in 1 hour

    6. Ensure user receives email to registered address

    7. User Completes Reset

    8. User clicks link in email
    9. Sets new password

    10. Password meets requirements:

      • Minimum 12 characters
      • Mix of uppercase, lowercase, numbers, symbols
      • Not in common password list

    11. Verify Reset 

      # Test login with new password
curl -X POST https://api.codex.local/api/v1/auth/login \
  -d '{"username":"alice", "password":"NewSecurePass123!"}'

    Troubleshooting: - Email not received: Check spam folder, verify email in system - Reset link expired: Create new reset request - Password doesn't meet requirements: Show specific requirement failed

    Duration: 5-10 minutes

    Runbook 2: Enable MFA for User¶

    Scenario: User requests MFA or system requires it

    Prerequisites: - User has authenticator app (Google Authenticator, Authy, etc.) - System admin or user themselves

    Steps:

    1. User Initiates MFA Setup 

      POST /api/v1/auth/mfa/setup
Content-Type: application/json
Authorization: ******

{}  # Empty body

Response:
{
  "secret": "JBSWY3DPEBLW64TMMQ======",
  "qr_code_url": "otpauth://totp/Codex:alice@company.com?secret=..."
}

    2. User Scans QR Code

    3. User opens authenticator app
    4. Scans QR code (or manually enters secret)

    5. Authenticator displays 6-digit code

    6. Verify Code 

      POST /api/v1/auth/mfa/verify
{
  "code": "123456"
}

    7. Save Backup Codes

    8. System generates 10 backup codes (single-use)
    9. User stores safely (password manager, paper)

    10. Used if authenticator is unavailable

    11. Confirm Setup 

      # MFA is now enabled
# Required on next login

    Verification: - Force logout user - User logs in again - System prompts for MFA code - User enters code from authenticator - Login succeeds

    Duration: 10-15 minutes

    Runbook 3: Recover MFA-Locked Account¶

    Scenario: User lost authenticator or backup codes

    Prerequisites: - System admin role - Out-of-band identity verification - User has access to recovery email

    Steps:

    1. Verify Identity
    2. Confirm user identity via recovery email
    3. Ask security questions (if configured)

    4. Verify account ownership

    5. Disable MFA Temporarily 

      curl -X POST https://api.codex.local/api/v1/auth/mfa/disable \
  -H "Authorization: ******" \
  -d '{"user_id": "alice@company.com"}'

    6. Notify User

    7. Email notification that MFA was disabled

    8. User should re-enable ASAP

    9. User Re-Enables MFA

    10. Follow Runbook 2
    11. User sets up new authenticator

    12. Generates new backup codes

    13. Verify

    14. Confirm MFA working on next login

    Duration: 15-20 minutes

    Authorization Runbooks¶

    Runbook 4: Assign Role to User¶

    Scenario: New team member needs access level

    Prerequisites: - System admin role - User exists in system - Clear role requirements

    Steps:

    1. Verify Role Requirements
    2. What tasks will user perform?
    3. What resources will they access?

    4. What permissions are minimum necessary?

    5. Select Appropriate Role

    6. system_admin: Full platform control (rare)
    7. agent_operator: Deploy/manage agents
    8. ci_operator: Manage CI/CD pipelines
    9. security_reviewer: Approve security changes
    10. doc_maintainer: Manage documentation
    11. agent_reader: Read-only access

    12. guest: Public-only access

    13. Assign Role 

      POST /api/v1/governance/roles/assign
Authorization: ******
Content-Type: application/json

{
  "user_id": "bob@company.com",
  "role": "agent_operator"
}

Response:
{
  "user_id": "bob@company.com",
  "role": "agent_operator",
  "assigned_at": "2026-07-08T16:30:00Z",
  "assigned_by": "admin@company.com"
}

    14. Verify Permissions 

      GET /api/v1/governance/rbac/permissions?user_id=bob@company.com

Response:
{
  "user_id": "bob@company.com",
  "roles": ["agent_operator"],
  "permissions": {
    "agents": ["create", "read", "update", "execute"],
    "workflows": ["create", "read", "update", "execute"],
    "secrets": ["read"],
    ...
  }
}

    15. Confirm Access

    16. User logs in
    17. User can access assigned resources

    18. User gets 403 for unauthorized resources

    19. Document in Ticket

    20. Record reason for role assignment
    21. Link to approval/ticket
    22. Update access control list (ACL)

    Duration: 5-10 minutes

    Runbook 5: Revoke User Access¶

    Scenario: Employee departure, lateral move, role change

    Prerequisites: - System admin role - Manager approval - User identified

    Steps:

    1. Verify Revocation Authorization
    2. Get manager approval
    3. Confirm effective date

    4. Identify all access to revoke

    5. Revoke Role 

      POST /api/v1/governance/roles/revoke
Authorization: ******

{
  "user_id": "alice@company.com",
  "role": "agent_operator",
  "reason": "departee_sep_15",
  "effective_date": "2026-07-15T17:00:00Z"
}

    6. Revoke Active Tokens 

      POST /api/v1/auth/token/revoke-all
Authorization: ******

{
  "user_id": "alice@company.com",
  "reason": "access_revocation"
}

    7. Revoke API Tokens 

      GET /api/v1/auth/tokens?user_id=alice@company.com
# For each token created by user:
POST /api/v1/auth/token/revoke
{
  "token_id": "token_001"
}

    8. Verify Access Denied

    9. Verify user gets 403 when accessing resources

    10. Verify API tokens no longer work

    11. Archive Audit Records

    12. Export audit logs for user
    13. Store in cold storage (90+ days)

    14. Keep for compliance (SOX, HIPAA, etc.)

    15. Offboarding Checklist

    16. Credentials revoked
    17. API tokens revoked
    18. SSH keys revoked
    19. GitHub access removed
    20. VPN access disabled
    21. Audit logs archived
    22. Manager notified

    Duration: 10-15 minutes

    Runbook 6: Approve Sensitive Operation¶

    Scenario: Approval request pending for agent deployment, secret rotation, etc.

    Prerequisites: - Approver role - Request pending approval - Authority to approve

    Steps:

    1. Review Request Details 

      GET /api/v1/governance/approvals/{request_id}
Authorization: ******

Response:
{
  "request_id": "req-xyz-123",
  "policy_code": "AGENT_DEPLOY_PROD",
  "requester_id": "alice@company.com",
  "resource_id": "agent_prod_001",
  "context": {
    "agent_name": "DataProcessor",
    "version": "2.1.0",
    "change_summary": "Q3 ML model update"
  },
  "created_at": 1720000000,
  "expires_at": 1720000300,
  "status": "pending"
}

    2. Review Change Details

    3. Verify requester identity
    4. Review proposed change
    5. Check against security policies

    6. Assess risk level

    7. Make Decision

    Approval: 

    POST /api/v1/governance/approvals/{request_id}/approve
Authorization: ******
Content-Type: application/json

{
  "reason": "Change reviewed and validated against security policies",
  "notes": "ML model evaluated on Q3 dataset"
}

    Rejection: 

    POST /api/v1/governance/approvals/{request_id}/reject
Authorization: ******

{
  "reason": "Model has not been validated against Q3 requirements"
}

    1. Document Decision
    2. Provide clear reason in approval/rejection
    3. Allow requester to address concerns (if rejected)

    4. Note any conditions or requirements

    5. Confirm Action

    6. If approved: verify action executes
    7. If rejected: requester resubmits after changes
    8. Monitor execution (if applicable)

    Duration: 5-20 minutes (depends on review complexity)

    Secret Management¶

    Runbook 7: Rotate API Key/Secret¶

    Scenario: Monthly rotation, credential compromise, team member departure

    Prerequisites: - System admin or security_reviewer role - Service account or user identified - Planned maintenance window

    Steps:

    1. Prepare Rotation Plan
    2. Identify all dependent services
    3. Planned maintenance window

    4. Rollback procedure

    5. Generate New Secret 

      POST /api/v1/auth/tokens
Authorization: ******

{
  "name": "DataPipeline Service (rotated)",
  "scopes": ["api:agents:read", "api:workflows:exec"],
  "expires_in": 7776000  # 90 days
}

Response:
{
  "token": "codex_pat_xyz789abc456",
  "created_at": 1720000000,
  "expires_at": 1727776000
}

    6. Store New Secret Securely

    7. Save to secret manager (HashiCorp Vault, AWS Secrets Manager, etc.)
    8. Do NOT share via email or chat

    9. Encrypt before storing

    10. Test New Secret

    11. Use new secret in staging environment
    12. Verify all integrations work

    13. Monitor for errors

    14. Deploy New Secret

    15. Update dependent services with new secret
    16. Stage deployment (1 service at a time)

    17. Monitor for issues

    18. Verify All Integrations 

      # Verify each service using new secret
curl -H "Authorization: ******" \
  https://api.codex.local/api/v1/agents

# Should get 200 OK response

    19. Revoke Old Secret 

      POST /api/v1/auth/token/revoke
Authorization: ******

{
  "token_id": "old_token_id"
}

    20. Document Rotation

    21. Record date of rotation
    22. Note reason (monthly/compromise/offboarding)
    23. Update runbook if needed

    Timeline: - Test: 1 hour - Deploy: 1-2 hours - Verification: 30 minutes - Total: 2.5-3.5 hours

    Runbook 8: Respond to Exposed Secret¶

    Scenario: Secret accidentally committed, exposed in logs, or compromised

    Prerequisites: - Discovery of exposure (GH secret scanning, log review, etc.) - System admin role

    Steps:

    1. Assess Exposure Severity
    2. What secret was exposed? (API key, password, encryption key)
    3. Where was it exposed? (GitHub, logs, Slack)
    4. How long was it exposed?

    5. Was it accessed by unauthorized parties?

    6. Immediate Containment (< 5 min) 

      # Revoke exposed secret immediately
POST /api/v1/auth/token/revoke
Authorization: ******

{
  "token_id": "exposed_token_id",
  "reason": "compromised"
}

    7. Remove from Public Sources

    8. Force-push to remove from Git history (if applicable)
    9. Delete from GitHub gists/issues

    10. Remove from Slack/email logs

    11. Issue New Secret

    12. Follow Runbook 7
    13. Deploy to all dependent services

    14. Verify functionality

    15. Investigation (if needed)

    16. Audit logs: Who had access? What did they do?
    17. Monitor: Unauthorized use of exposed secret

    18. Threat assessment: Was it exploited?

    19. Notification (compliance requirement)

    20. Notify affected users/services
    21. Provide timeline and impact assessment

    22. Recommend password changes (if user credentials)

    23. Post-Incident Review

    24. Root cause: How was it exposed?
    25. Prevention: Enhanced controls (secret scanning in pre-commit)
    26. Document: Add to incident tracking system

    Duration: 15-60 minutes (depends on exposure scope)

    Incident Response¶

    Runbook 9: Unauthorized Access Detected¶

    Scenario: Suspicious login, token misuse, or permission denial spike

    Prerequisites: - Security team notified - Incident commander assigned - System access credentials

    Steps:

    1. Immediate Triage (< 5 min)
    2. Confirm alert is real (not false positive)
    3. Determine affected user/service

    4. Assess scope (single user vs. widespread)

    5. Contain Threat (< 15 min) 

      # Option 1: Revoke user sessions (minimal impact)
POST /api/v1/auth/token/revoke-all
{
  "user_id": "compromised_user@company.com"
}

# Option 2: Disable user account (maximum containment)
POST /api/v1/users/disable
{
  "user_id": "compromised_user@company.com",
  "reason": "suspicious_activity"
}

    6. Gather Evidence 

      # Extract audit logs for investigation
GET /api/v1/audit-logs?user_id=compromised_user@company.com&hours=24

# Get failed permission checks
GET /api/v1/audit-logs?event_type=permission_denied&hours=24

# Timeline of all actions
GET /api/v1/audit-logs?user_id=compromised_user@company.com&sort=desc

    7. Communicate

    8. Notify incident commander
    9. Update status in incident tracking

    10. Prepare status for stakeholders

    11. Investigation

    12. What actions did attacker/compromised user perform?
    13. Were any sensitive operations executed?
    14. Were any secrets accessed?

    15. Which systems were impacted?

    16. Remediation

    17. Reset user password
    18. Re-enable MFA
    19. Review and revoke suspicious API tokens

    20. If internal threat: escalate to HR/legal

    21. Recovery

    22. Monitor system for residual activity
    23. Check for privilege escalation attempts

    24. Verify logs are clean for 24 hours

    25. Post-Incident

    26. Document incident timeline
    27. Root cause analysis
    28. Preventive measures implemented
    29. Lessons learned

    Duration: 30 min - several hours (depends on severity)

    Runbook 10: Malicious Deployment Detected¶

    Scenario: Unauthorized or suspicious agent deployed to production

    Prerequisites: - Alert triggered (unusual deployment pattern, approval bypass) - Incident commander assigned

    Steps:

    1. Verify Deployment (< 2 min) 

      # Get deployment details
GET /api/v1/agents/{agent_id}/versions/{version}

# Check approval history
GET /api/v1/governance/approvals?resource_id={agent_id}

    2. Rollback Deployment (< 5 min) 

      # Immediate rollback to previous version
POST /api/v1/agents/{agent_id}/rollback
Authorization: ******

{
  "target_version": "previous_stable_version",
  "reason": "security_incident"
}

# Monitor rollback progress
GET /api/v1/agents/{agent_id}/deployments/{deployment_id}

    3. Disable Agent (if needed) 

      POST /api/v1/agents/{agent_id}/disable
{
  "reason": "security_incident",
  "duration_minutes": 60  # Temporary disable
}

    4. Investigation

    5. Who deployed it? (audit logs)
    6. Was approval properly obtained?
    7. What did the agent do? (code review)
    8. Who approved it? (approval audit)

    9. Was approval workflow bypassed?

    10. Containment 

      # Review approver's actions
GET /api/v1/audit-logs?user_id={approver_id}&hours=24

# Check for other suspicious deployments
GET /api/v1/agents/deployments?status=recent&hours=24

    11. Communication

    12. Notify users impacted by deployment
    13. Provide status of remediation

    14. Give timeline for agent restoration

    15. Recovery

    16. Monitor previous stable version in production
    17. Collect evidence from malicious version (code, logs)
    18. Once investigation complete, re-enable agent

    Duration: 15-60 minutes + investigation

    Audit & Compliance¶

    Runbook 11: Generate Compliance Report¶

    Scenario: Annual audit, SOC 2 assessment, compliance requirement

    Prerequisites: - System admin or compliance officer role - Audit scope defined (date range, resources)

    Steps:

    1. Define Audit Scope
    2. Date range (last 90 days, calendar year, etc.)
    3. Resources (all agents, specific agents, APIs)

    4. Event types (deployments, approvals, access)

    5. Query Audit Logs 

      GET /api/v1/audit-logs?start_date=2026-04-08&end_date=2026-07-08

# Filter by event type
GET /api/v1/audit-logs?event_type=agent_deployed&hours=2160  # 90 days

# Filter by resource
GET /api/v1/audit-logs?resource_type=agents&resource_id=prod_agents

    6. Generate Report 

      # Export audit logs to CSV for analysis
audit_logs = query_audit_logs(...)

report = {
  "period": "2026-04-08 to 2026-07-08",
  "total_events": len(audit_logs),
  "deployments": count_by_event_type("agent_deployed"),
  "approvals": count_by_event_type("approval"),
  "failed_access": count_by_event_type("permission_denied"),
  "role_changes": count_by_event_type("role_changed"),
}

    7. Prepare Report

    8. Summary of activities
    9. Breakdown by event type
    10. User access matrix
    11. Approval latency metrics
    12. Security events (failed access, denied permissions)

    13. Compliance findings

    14. Review & Sign-off

    15. Review with security team
    16. Compliance officer approval
    17. Audit team sign-off

    Duration: 2-4 hours
